# 06. UniRig 자동 리깅: 격리 런타임과 텍스처 보존

> 이 문서는 AI가 프로젝트 개발 과정에서 작성한 기술 학습 기록입니다. 특정 개발 장비, 계정, 개인 경로 또는 실제 사용자 자산은 기록하지 않습니다.

## 문제

자동 리깅은 정적 GLB를 받아 골격과 스키닝 가중치를 생성해야 합니다. 그러나 UniRig는 데스크톱 앱이 사용하는 Python/AI 라이브러리와 다른 네이티브 확장 및 패키지 조합을 요구합니다. 이 의존성을 메인 PySide6 환경에 직접 설치하면 재구성 모델, VTK 또는 NumPy/PyTorch의 import 순서가 깨질 수 있습니다.

또한 UniRig의 중간 결과는 FBX 중심입니다. FBX 결과만 내보내면 원본 GLB의 재질과 텍스처 참조가 빠질 수 있어, 텍스처 모델을 리깅한 뒤 단색 모델처럼 보이는 문제가 생깁니다.

| 위험 | 잘못된 접근 | 결과 |
| --- | --- | --- |
| 패키지 충돌 | 메인 `.venv`에 UniRig 의존성을 함께 설치 | 데스크톱 앱 또는 재구성 공급자 import 실패 |
| GPU 메모리 충돌 | 재구성/텍스처 모델이 남은 상태에서 리깅 로드 | VRAM 부족 또는 UI 응답 저하 |
| 텍스처 소실 | UniRig가 만든 FBX만 최종 산출물로 사용 | 재질·이미지가 누락된 리깅 결과 |
| 온라인 재다운로드 | 추론 중 모델 ID로 원격 저장소 호출 | 예기치 않은 다운로드, 재현 불가 실행 |

## 채택한 구조

```text
메인 PySide6 앱
  └─ Qt 리깅 작업 스레드 (상태/진행/취소 담당)
       └─ UniRig 격리 Python 자식 프로세스
            1. GLB 입력 정규화
            2. CUDA Skeleton 생성
            3. CUDA Skinning Weight 생성
            4. 원본 텍스처 GLB로 병합
       └─ 결과 GLB + 로그 + 종료 코드
  └─ 독립 Rig Validation → Rig/Animate 화면 갱신
```

이 구조는 서버가 아닙니다. 자식 프로세스는 앱이 시작하고 종료하며, 네트워크 포트를 열지 않습니다. 입출력은 프로젝트 내부의 파일, 표준 로그, 종료 코드로만 처리합니다.

## 구축 방법

### 1. 소스·가중치·런타임의 분리

| 구성 | 위치 원칙 | 역할 |
| --- | --- | --- |
| 공급자 소스 | `external/UniRig` | upstream 코드와 설정 |
| 격리 환경 | 공급자 소스 아래의 전용 Python 환경 | UniRig 전용 PyTorch/확장 |
| 체크포인트 | 프로젝트 로컬 캐시 | Skeleton/Skinnig 모델, 변환기 모델 |
| 데스크톱 환경 | 프로젝트의 기본 `.venv` | PySide6, VTK, 재구성 UI |

앱은 절대 경로나 사용자 폴더를 코드에 저장하지 않습니다. 설정 계층이 프로젝트 데이터 루트에서 공급자 소스·캐시·실행 파일을 해석합니다.

### 2. 단계별 실행

1. 정적 GLB를 복사해 공급자 입력으로 고정합니다. 원본 수용 모델은 수정하지 않습니다.
2. 입력 정규화 단계에서 UniRig가 처리 가능한 메쉬 표현을 생성합니다.
3. Skeleton 단계가 관절 계층을 생성합니다.
4. Skinning 단계가 각 정점의 관절 영향과 가중치를 생성합니다.
5. 텍스처 병합 단계가 스키닝 FBX 정보를 **원래 텍스처 GLB**에 적용해 새 rigged GLB를 생성합니다.
6. 독립 리그 검증을 통과한 결과만 화면에 게시합니다.

### 3. FlashAttention의 단계별 처리

UniRig의 Skeleton과 Skinning은 동일한 네이티브 확장을 같은 방식으로 요구하지 않을 수 있습니다. 따라서 Skeleton 단계에서는 Windows 호환성 문제가 되는 FlashAttention을 비활성화하고, Skinning 단계에서만 프로젝트 로컬 캐시의 검증된 wheel을 설치합니다.

이 조치는 다음을 보장합니다.

- 메인 앱 환경을 수정하지 않습니다.
- 온라인 `pip install`을 추론 중 수행하지 않습니다.
- 필요한 단계에만 네이티브 확장을 노출합니다.
- 각 실행이 끝나면 자식 프로세스와 GPU 참조가 종료됩니다.

## 검증 기준

| 검증 | 통과 조건 |
| --- | --- |
| 준비 상태 | 격리 실행 파일, 소스, 로컬 체크포인트, CUDA, 필요한 확장이 모두 확인됨 |
| 실제 리깅 | GPU에서 Skeleton과 Skinning 단계가 실행됨 |
| GLB 구조 | root joint, 부모-자식 계층, skin, inverse bind matrix 존재 |
| 스키닝 | `JOINTS_0`, `WEIGHTS_0` 인덱스·가중치가 유효하고 변형 스모크가 성공 |
| 텍스처 | 최종 GLB가 원본 material/image/texture 참조를 유지 |
| UI | 작업 중 Create Rig가 중복 실행되지 않고 완료/실패 후에만 다시 활성화 |

## 운영 시 주의점

- UniRig의 8 GiB 기준은 이 격리 공급자에 대한 재현된 준비 기준일 뿐, Hunyuan3D 또는 SkinTokens/TokenRig의 VRAM 기준을 낮추지 않습니다.
- 실패한 리깅은 수용된 정적 모델을 무효화하지 않습니다.
- 중간 산출물이나 로그가 남더라도, Rig Validation을 통과하기 전에는 성공 리그로 표시하면 안 됩니다.
- 복잡한 모델에서는 단계별 제한 시간을 두고, 취소 시 자식 프로세스 트리까지 종료해야 합니다.
