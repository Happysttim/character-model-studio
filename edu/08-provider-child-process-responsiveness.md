# 08. 무거운 AI 작업에서 앱 응답성을 지키는 자식 프로세스 설계

> 이 문서는 AI가 프로젝트 개발 과정에서 작성한 기술 학습 기록입니다. 특정 사용자 파일, 경로, 장비 식별자는 포함하지 않습니다.

## 문제

Qt의 `QThread`로 작업을 옮겨도 모든 경우에 GUI 프로세스가 완전히 안전한 것은 아닙니다. 일부 연구용 Python 공급자는 장시간 CUDA 호출, 네이티브 확장, Python GIL 점유, 대규모 메모리 할당을 수행합니다. 그 결과 UI 스레드는 논리적으로 분리되어 있어도 Windows가 창을 “응답 없음”으로 판단할 수 있습니다.

특히 다음 작업이 위험했습니다.

| 작업 | 원인 | 영향 |
| --- | --- | --- |
| Hunyuan3D-2GP Paint/UV bake | 무거운 Texture/렌더링 네이티브 연산 | 메인 Qt 프로세스가 장시간 불안정 |
| UniRig Skeleton/Skinning | 별도 확장 및 공급자 전용 런타임 | 기본 앱 환경과 의존성 충돌 가능 |
| 대형 GLB 검증 | 연결 요소 분할처럼 메쉬를 복사하는 분석 | CPU 메모리 부족으로 검증 실패 |

## 설계 원칙

```text
Qt UI
  → Qt worker: 상태/진행/취소 요청
  → application-owned child Python
      → CUDA 또는 공급자 전용 네이티브 작업
      → 결과 파일, 로그, 종료 코드
  → parent: 출력 존재/검증 후 UI에 게시
```

- 자식 프로세스는 필요할 때만 시작하고 작업이 끝나면 종료합니다.
- HTTP, socket, daemon, 별도 백엔드는 사용하지 않습니다.
- 공급자는 오직 명시된 로컬 캐시와 외부 소스를 사용하고, 추론 중 다운로드하지 않습니다.
- 부모 앱은 진행 메시지, 취소, 타임아웃, 종료 코드를 관리합니다.
- 출력 GLB가 존재한다는 이유만으로 성공 처리하지 않고, Model/Rig Validation을 통과한 뒤 게시합니다.

## 취소와 타임아웃

작업 취소는 단순 버튼 상태 변경이 아니라 실제 자식 프로세스와 그 하위 프로세스를 종료해야 합니다. 그렇지 않으면 CUDA를 점유한 공급자 또는 변환 도구가 남아 다음 작업을 방해할 수 있습니다.

| 상황 | 부모 앱의 처리 |
| --- | --- |
| 정상 종료 + 유효 출력 | 검증 후 성공 게시 |
| 비정상 종료 | 로그 마지막 부분을 진단에 보존하고 실패 상태 게시 |
| 시간 초과 | 프로세스 트리 종료, 부분 산출물은 성공으로 게시하지 않음 |
| 사용자가 취소 | 프로세스 트리 종료, `CANCELLED` 처리, 이전 수용 자산 보존 |
| 출력 생성 후 프로세스 정지 | 출력 안정성 확인 후 종료, 별도 검증 수행 |

## Qt 작업 스레드 종료 순서

Mock 작업도 실제 앱과 같은 `QThread` 수명 규칙을 따라야 합니다. 작업 완료 신호를 받은 즉시 마지막 Python 참조를 버리면, Windows에서 Qt의 native thread 종료와 객체 삭제가 경합할 수 있습니다. 완료 슬롯에서는 QThread를 지역 변수로 잠시 유지하고, terminal signal을 전달한 뒤 `deleteLater()`로 Qt 이벤트 루프에 폐기를 맡깁니다.

이 규칙은 Mock 결과를 실제 CUDA 결과로 위장하기 위한 것이 아닙니다. Mock과 실제 공급자가 동일한 UI/작업 수명 계약을 지키도록 해, 테스트가 실제 앱의 종료·신호 순서를 더 잘 검증하게 합니다.

## 대형 GLB 검증의 별도 교훈

`trimesh.split()` 같은 연결 요소 분석은 대형 메쉬를 여러 복사본으로 만들 수 있습니다. GPU 재구성이 성공했더라도 이 CPU 검증 단계가 `MemoryError`로 실패할 수 있습니다.

따라서 핵심 안전성 검사는 계속 수행하되, 고비용 진단은 크기 기준으로 건너뛰고 `PASS_WITH_WARNINGS`로 기록합니다. 이는 GPU 추론을 CPU fallback으로 대체하는 것이 아니라, 이미 생성된 자산의 비본질적 분석을 메모리 안전하게 조정하는 것입니다.

## 확인 방법

1. Texture 또는 Rig 작업 중 Processing 로그가 계속 갱신되는지 확인합니다.
2. 창 이동, 화면 전환, 취소가 가능해야 합니다.
3. 자식 프로세스 종료 뒤 다음 CUDA 단계가 시작될 수 있는지 확인합니다.
4. 실패 시 정적 모델·수용된 리그·저장된 포즈가 유지되는지 확인합니다.
5. 성공 시 결과 GLB, validation report, 공급자/단계 로그가 프로젝트 상대 경로로 연결되는지 확인합니다.
